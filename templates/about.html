About Clinic Visit Sorter

Architecture, Safety Safeguards & College Project Viva Guide

1. Project Overview & Scope

Clinic Visit Sorter is an AI-assisted health administration and queue triage application designed for college clinics. It reads student-reported symptoms written in informal English, Tamil, and Tanglish, classifies them using AI with strict JSON schemas, applies clinical safety override rules, and organizes patients into an actionable nurse queue.

Crucial Safety Principle: The system is designed to organize the queue only. It never diagnoses diseases, never prescribes medications, and never removes any student from the queue. A human nurse makes all medical decisions.

2. Core Safety Safeguards

  • Deterministic Red-Flag Detection: Regex/substring checks in Python catch high-risk phrases (e.g. "chest pain", "fainted", "moochu vida mudiyala", "nenju valikuthu") and immediately assign see_now. The AI is forbidden from lowering this.
  • Dizziness & Nosebleed Guard: Notes mentioning dizziness or nosebleeds must receive at least today and can never be marked routine.
  • Missing / Short Notes: Notes under 3 characters or empty notes default to today to ensure nurse verification.
  • Strict No-Diagnosis Enforcement: Summaries are limited to 12 words of reported symptoms only. If the AI attempts to guess a disease (e.g., dengue, typhoid) or speculative words (likely, suspected), Python sanitizes it to "Symptoms reported, nurse to assess".
  • Fault-Tolerant Fallback: If the API fails or is unconfigured, the app falls back safely without crashing: category=other, priority=today, summary="Could not classify, nurse to review".

3. College Viva Examination Questions & Answers

Q1: Why is an LLM used here instead of simple keyword matching?

Answer: Students report health complaints informally with typos, colloquialisms, and code-mixed Tanglish (e.g., "lab la chemical vilunthu finger itching aguthu"). LLMs excel at semantic understanding and summarization without needing exhaustive rule lists for every typo. However, for critical red-flag symptoms, deterministic rule-based checks act as a safety net.

Q2: Why is a priority that is too high better than a priority that is too low?

Answer: A priority that is too high (false positive) costs the nurse only a few extra minutes of attention. A priority that is too low (false negative) could leave a student suffering from acute chest pain or anaphylaxis waiting behind administrative requests, leading to severe clinical risk. Thus, when uncertain, the system always elevates priority.

Q3: How does the application prevent hallucinations or disease guessing?

Answer: We enforce three layers: (1) System prompt instructions forbidding diagnosis; (2) JSON Schema validation restricting outputs; (3) Post-processing Python sanitation that scans for forbidden medical diagnosis terms and speculation words, replacing them with neutral symptom descriptions.

Q4: What happens if the API key is missing or the network disconnects?

Answer: The app implements graceful degradation. It never crashes. A missing API key or timeout activates the fallback classification (category=other, priority=today), while the local Python red-flag module continues detecting emergency phrases and assigning see_now.

Q5: How is sorting executed?

Answer: Multi-level stable sorting: primary key is urgency rank (see_now = 0, today = 1, routine = 2), and secondary key is parsed arrival timestamp (HH:MM). This ensures fair, first-come-first-served order within urgency tiers.
